# 课堂集群实验室 (cluster-lab)

一个贯穿全课程的分布式系统演示工具。**只用 Python 标准库和浏览器**，不需要 pip、
不需要 Node，也不参与课件构建。

需要 **Python 3.10 或更高版本**（代码使用 `X | Y` 类型写法与结构化模式匹配语法）。
开讲前先自检一次：

```bash
python3 -c "import sys; assert sys.version_info >= (3, 10), sys.version; print('ok', sys.version.split()[0])"
```

```bash
python3 lab/run.py serve
```

浏览器会自动打开 <http://127.0.0.1:8000/>。左侧选演示，右侧改参数，中间看动画。
8000 端口被占用时换一个：

```bash
python3 lab/run.py serve --port 8123
```

`--no-open` 可以不自动打开浏览器；服务只绑定回环地址，不对外提供访问。

## 它是怎么工作的

一句话：**Python 是唯一的真相来源，网页只负责回放。**

```
python3 lab/run.py …  ──►  确定性内核 ──►  一条完整的事件轨迹 (trace JSON)
                                              │
                    浏览器 ◄─────────────────┘  只做回放：不含任何协议逻辑
```

因此课堂动画、命令行输出、单元测试和实验报告看到的是同一份证据；
`(演示, 参数, 种子)` 一旦相同，轨迹逐字节相同，动画也逐帧相同。

内核使用整数逻辑时钟与最小堆，全程不读墙上时间、不调用 `sleep`；
所有随机决定来自同一个 `Random(seed)`。播放速度只是回放倍率，不影响结果。

## 界面

| 区域 | 作用 |
|---|---|
| 左栏 | 演示菜单，按讲次分组 |
| 舞台 | 视图标签页；每个演示只显示它用得上的那几个 |
| 时间轴 | 播放 / 暂停 / 单步 / 拖动 / 调速 |
| 教学要点 | 剧本在关键时刻抛出的讲解卡片 |
| 事件日志 | 逐条事件；勾选“全部消息”可看每一次收发 |
| 右栏 | 先猜后验、参数表单、不变式结果、指标 |

快捷键：`空格` 播放/暂停，`←`/`→` 上一/下一事件，`R` 重跑，`P` 投影模式，`1–9` 切换演示。

- **阶段暂停**：默认打开。播放到**阶段标记**（每一幕的开头）与**警告 / 违规**要点时自动停下，
  方便讲解；普通讲解要点会出现在卡片里但不打断播放，以免每隔几秒就卡一次。
- **投影模式**：隐藏侧栏、放大字号，适合大屏。
- **导出图形 / 导出轨迹**：SVG（当前视图）可直接放进幻灯片；JSON 是可引用的原始数据。
- **跳到反例**：检查器给出反例时，可一键把播放头拖到那一刻；客户端历史里的相关操作会被圈出。

### 六个视图

- **集群 cluster**：节点按角色或事务状态着色（Leader / Candidate / prepared / committed …），
  消息以小球沿边飞行，被丢弃的消息半途消散并标出原因；
  下方日志矩阵按“行=节点、列=日志索引”排布，已提交条目有绿色下划线，
  被覆盖的条目会被划掉并标注“被覆盖”，压缩掉的前缀显示为一条“快照 ≤ N”的色带。
- **客户端历史 history**：每个操作一根条，`ok` / `unknown` / `fail` 三色；
  横轴是**事件时间**（每个调用与返回各占一格），因此 15 个 tick 的操作在 2600 tick 的运行里依然看得清；
  分区期间有底色，检查器的最小反例会被标为“反例”。
- **时空图 timeline**：进程泳道 + 消息斜箭头，每个事件下方标注当前所选时钟的读数；
  检查器指出的那一对事件会被圈出来。
- **分片 shards**：路由器把键发往分片，下方柱状图按播放头累计各分片负载，
  虚线是声明出来的均衡阈值；按过期路由送达的请求会把分片框标红。
- **日志与恢复 storage**：预写日志条带（未落盘的尾部是虚线且半透明）、
  磁盘页面与缓冲池页面**分两行并列**——它们不一致正是重点，
  外加恢复阶段徽标、扫描指针与事务表（winner / loser）。
- **算子与数据流 dataflow**：算子按层自上而下排布，边上标着行数与字节数，
  当前阶段的边有数据点在流动；每一层输入最大的那个算子被标成「最慢」——
  查询等的是最慢的分区，不是平均值。

## 三分钟课堂脚本

> 下面每个脚本里出现的具体数字都对应**默认参数 + 默认种子 2026**。
> 这些数字由 `tests/test_lab.py::InstructorScriptFiguresTests` 固定，
> 改动实现而忘了改讲稿会让测试失败。上课时仍请以界面右侧的实时指标为准。

### 绪论 · 确认是何意味 (`ack-meaning`)

1. **先猜后验**：把右上角的问题读给学生，让他们举手选。
2. 默认参数（多数派确认 + 复用 request_id）跑一遍：全部不变式通过。
3. 把「确认点」切到 **Leader 本地落盘即回复**，再跑：
   `已确认写不丢失` 变红——客户端手里那个 ok 指向一条被截断的日志。
4. 把「重试策略」切到 **每次重试生成新的 request_id**：
   `同一操作至多生效一次` 变红，计数器从 3 跳到 4。
5. 收尾：ok 的含义由确认点定义；超时只能推出 unknown；重试必须复用请求编号。

### 第1讲 · 四种时间 (`four-clocks`)

1. 先猜后验：Lamport 时间戳满足 `C(a) < C(b)`，能断定 a 导致了 b 吗？
2. 事件脚本是固定的，因果关系完全已知——它就是标准答案。默认用**物理时钟**：
   `b1` 的读数是 160，它导致的 `c2` 却是 90，两个事件被圈出来标成反例。
3. 换成 **Lamport**：因果顺序对了，但并发判定仍然错——它给出的是全序。
4. 换成 **向量时钟**：两项都对，代价写在指标里（每个事件 3 个整数）。
5. 换成 **HLC**：跟随墙上时钟、保住因果方向，但仍是标量，识别不了并发。
6. 收尾：把物理时钟的偏差关掉，因果不再被弄反——**但同步是一个假设，不是事实。**

### 第1讲 · 相同日志，不同状态 (`nondeterministic-apply`)

1. 先猜后验：三个副本收到逐字节相同的日志，状态一定相同吗？
2. 默认在 `apply()` 里现场生成 token（相当于调用 `random()` 或读本地时钟）：
   日志矩阵三行完全一样，状态却是 `A@280` / `B@320` / `C@317` 三种。
3. 换成“排序前决定”：同样的三行日志，状态收敛成一个。
4. 收尾：Raft 保证的是日志一致，不是应用结果一致；共识层对这种发散一无所知。

### 第2讲 · Raft 选举 (`raft-election`)

1. 先猜后验：隔离当前 Leader 之后，最多有几个自称 Leader 的节点？
2. 播放。第一幕看随机超时如何打破对称，第二幕看被隔离的 Leader 继续自称 Leader。
3. 指出 `每个任期至多一个 Leader` 仍然通过——安全性约束的是任期，不是时刻。
4. 换几个种子，看选举轨迹如何改变而结论不变。

### 绪论 · 分区期间的选择 (`cap-partition`)

1. 先猜后验：两侧都接受写入，最先被打破的是哪一条？
2. 默认 **CP**：分区期间少数派一侧的写与读变成 unknown，全部不变式通过。
3. 切到 **AP**：两侧都回复成功，随后线性一致检查器给出最小反例
   （一次写 3 完成之后，读却返回 2），已确认写也没能留在多数派上。
4. 切到「客户端历史」标签页，指着被圈出的三根条讲：这就是证据本身。

### 第2讲 · 日志复制与提交规则 (`raft-replication`)

1. 保持 `figure8` 模式，先用 **Raft 规则** 跑完，注意 (e) 幕的教学要点。
2. 只把「提交规则」换成 **错误规则**，其他一律不动，再跑一遍。
3. 对照日志矩阵：两次运行的**最终日志完全相同**，唯一的差别是那个提交标记。
4. 错误规则下，索引 2 的条目被划掉并标注“被覆盖”，
   `已提交前缀不被推翻` 给出反例（点“跳到反例”可直接跳到那一刻）。
5. 收尾：复制得多 ≠ 已经提交。

> `figure8` 为受控编排：关闭自发选举超时、由剧本触发换届，用于稳定复现论文场景。
> 想看自然调度，切到「常规复制」模式。

### 第2讲 · 读路径 (`read-path`)

1. 先猜后验：被隔离的旧 Leader 收到读请求，哪种协议会返回陈旧值？
2. 默认 **直接从 Leader 读**：旧 Leader 用本地状态作答，返回 x=1，线性一致被打破。
3. 换 **ReadIndex**：它无法与多数派确认领导权，于是这次读超时成为 unknown——可用性下降，但不撒谎。
4. 换 **租约读**：旧 Leader 明确拒绝服务（fail）。再把「旧 Leader 时钟倒退」打开，
   它以为租约仍然有效，又开始返回陈旧值——租约的安全性押在时钟假设上。
5. 换 **Follower Read**：多数派一侧的 Follower E 先取 ReadIndex、追上提交位置，
   然后返回正确的 x=2。指标里的「读取应答方」写着 `op-4→E`：
   **读副本描述的是位置，不是一致性等级。**

### 第4讲 · 两阶段提交 (`two-phase-commit`)

1. 先猜后验：协调者持久化 commit 之后立刻崩溃，客户端会看到什么？
2. 默认配置：决议已写下、通知未送出。参与者停在 `prepared` 持锁等待，
   并周期性地向已经死掉的协调者询问决议；客户端拿到 **unknown，而事务其实已经提交**。
3. 把「是否恢复」关掉：运行结束时参与者仍然 prepared，
   而**安全性检查全部通过**——阻塞是活性 (liveness) 代价，不是安全性违反。这一点值得停下来讲。
4. 把决议日志换成 **复制**：备用协调者接管，「T1 阻塞时长」从 1892 tick 降到 1103 tick。
   决议可以被复制，但它仍然必须送达参与者：**“用了 Raft”推不出“非阻塞”。**
5. 把崩溃时机换成「写下决议之前」：没有决议存在，接管者可以安全地回滚。

### 第3讲 · 分片策略对比 (`shard-strategies`)

1. 先猜后验：把整个键做散列，负载摊平了，代价是什么？
2. 依次跑 **Range → Hash → 复合键 → 加盐**，每次只抄两个数：
   「最热/平均」和「普通租户扫描触及分片」。
3. 结果自己会说话：

   | 策略 | 最热/平均 | 热点租户扫描 | 普通租户扫描 |
   |---|---:|---:|---:|
   | Range | 3.83 ✗ | 1 | 1 |
   | Hash | 1.33 ✓ | 6 | 6 |
   | 复合键 | 4.00 ✗ | 1 | 1 |
   | 加盐 | 1.93 ✓ | 6 | **1** |

4. 收尾：**没有一种策略能同时把两个数压到最低。** 加盐只在热点键上付出局部性，
   这是它比整键散列更值得的地方。

### 第3讲 · 分裂、迁移与过期路由 (`rebalance-routing`)

1. 先猜后验：旧分片收到一个它已不再拥有的键的写入，直接执行会怎样？
2. 默认「回答范围已迁移」：客户端历史里能看到一次重定向，之后一切正常。
3. 换成「将错就错」：写入落在旧分片上，随后从正确分片读回来的还是旧值。
   `请求落到正确分片` 与 `线性一致` 同时变红，最小反例是三个操作。
4. 收尾：客户端缓存的路由一定会过期，这是常态；
   **路由错误必须是协议内可恢复的状态，不能当成一次普通的成功。**

### 第6讲 · 快照安装与追赶 (`snapshot-catchup`)

1. 先猜后验：刚恢复连接、尚未追上的副本收到强一致读，会怎样？
2. 播放：E 掉队期间 Leader 持续写入，应用位置每超过压缩阈值就把前缀换成快照
   （日志矩阵里出现「快照 ≤ N」色带）。
3. 网络恢复时，Leader 需要的前缀已经不在日志里，于是改发 InstallSnapshot，装完再补日志尾巴。
4. 紧接着那次 Follower Read 会一直等到追赶完成才回答——看客户端历史里那根特别长的条。
   **进程已启动 ≠ 副本可以对外服务。**
5. 把压缩阈值调成 0 再跑一次：不再有快照安装，副本只靠日志追赶，代价是日志无限增长。

### 第4讲 · 定序还是协调 (`order-vs-coordinate`)

1. 先猜后验：预先定序的做法在执行期间需要多少跨分片消息？
2. 三种做法跑同一批跨分片转账，中途崩掉一个分片再重启。记下这张表：

   | 做法 | 协调往返 | 执行期跨分片消息 | 总额守恒 |
   |---|---:|---:|---|
   | 不协调 | 12 | 0 | **✗ 3942 / 4000** |
   | 执行中协调 (2PC) | 24 | 113 | ✓ |
   | 执行前定序 (Calvin 式) | **6** | **0** | ✓ |

3. 重点讲两句：不协调最省消息，连普通丢包都扛不住；
   预先定序**没有取消共识**——那 6 次往返就是复制输入的开销，
   崩溃恢复靠的也是重放同一份输入。
4. 把「读写集」换成「依赖读取结果」：侦察往返从 0 变成每笔一次。
   确定性调度的前提是提前知道要碰哪些数据。

### 第5讲 · 分布式 Join 策略 (`join-strategies`)

1. 先猜后验：两表没有共置却选了本地 Join，会发生什么？
2. 默认（未共置 + 本地 Join）：结果只有 1727 行，正确答案是 6918 行。
   **没有报错，只是少了行。** 这是本演示最重要的一屏。
3. 换成 Broadcast 或 Repartition：行数对了，代价出现在网络字节上。
4. 把「右表行数」从 60 调到 1200：指标里的「更便宜的一种」从 Broadcast 翻到 Repartition，
   这就是交叉点。再把右表调大而不放宽内存上限，广播端会撞上内存检查。
5. 收尾：注意「最慢/平均」这一栏——总字节相同的两个计划，尾延迟可以差很远。

### 第5讲 · 下推与两阶段聚合 (`pushdown-aggregation`)

1. 先猜后验：局部平均值再平均一次，结果对吗？
2. 四档下推逐个跑，看跨网络字节：307200 → 69120 → 17280 → **128**。
   算子图里的行数一层比一层少。
3. 把聚合换成「局部求平均再平均」并保持完全下推：
   答案从 241.4074 变成 239.936，`聚合结果正确` 变红。
4. 换成「拆成 SUM 与 COUNT」：同样的下推程度，答案又对了。
5. 收尾：下推的前提是**聚合可合并**；AVG 必须拆开，中位数需要别的办法。

### 第6讲 · ARIES 恢复 (`aries-recovery`)

1. 先猜后验：一个页面带着尚未落盘的日志记录被写到磁盘，然后崩溃，恢复会怎样？
2. 默认（两条规则都遵守，第 6 步崩溃）：Analysis 分出 winner/loser，
   Redo **重演历史**（注意有的记录标「跳过」——`pageLSN` 已经反映过它了），
   Undo 撤销 loser 并写 CLR。恢复结果与预期一致。
3. 关掉第一条规则（**不管日志直接刷页**）：日志只剩到 LSN 4，
   磁盘上的 P1 却带着 `pageLSN 5` 和 `c=30`。分析阶段根本看不到 T2，
   于是这条未提交的修改永久留在了数据里。
   请指着并排的两行说：**日志已经解释不了磁盘。**
4. 关掉第二条规则（**先回复客户端再刷日志**），并把崩溃点调到第 8 步：
   T3 收到过提交成功，崩溃后却连提交记录都不存在。
5. 可选：打开「恢复途中再次崩溃」，对比写 CLR 与不写 CLR 的撤销步数。
   注意这是**工作量**差异，不是正确性差异——两者最终都恢复正确。

### 第7讲 · 验证回路 (`jepsen-loop`)

1. 这个演示和前面所有演示都不同：**它不是剧本，是一次搜索。**
2. 默认（直接从 Leader 读 + 随机分区）：搜索立刻找到反例，
   最小历史只有 2 个操作，反例种子写在指标里——把它加进回归测试。
3. 换成 ReadIndex 或 Follower Read，把种子数调到 20：搜完一个反例都没有。
   这时请**逐字**读那条结论：“这不是正确性证明。”
4. 把故障注入关掉，读协议保持「直接从 Leader 读」：同样找不到反例。
   没有被隔离的旧 Leader，就没有陈旧值可读——**反例需要故障才会出现**。
5. 收尾：四个部件缺一不可（生成器、nemesis、完整历史、检查器）；
   固定种子提供重放，不提供覆盖率。

### 第8讲 · 架构镜头 (`architecture-lenses`)

1. 五种架构轮流跑一遍，每次只问四个问题——它们就写在右侧指标里：
   谁分配顺序、冲突何时发现、成功之前还要等什么、成功之后还有什么异步工作。
2. **Spanner 式**：等待（commit wait）发生在回复之前，关键路径最长，回复之后没有欠账。
3. **Calvin 式**：协调被提到执行之前，关键路径 8 步，执行期间分片之间零消息。
4. **TiDB 式 / CockroachDB 式**：客户端拿到成功之后仍有必须完成的工作
   （次要键提交、意向解析）。
5. 收尾：比较架构不是比较功能列表，而是看协调与等待被安排在路径的哪一段。

> 这是教学化的路径模型，不代表任何产品的实测行为，也不能用于性能比较。

`run` 在出现不变式反例时返回退出码 1，可以直接用在回归脚本里。
`sweep` 用来演示“固定种子提供重放，不提供覆盖率”：把反例种子记下来，加进回归测试。

```bash

```

还有一套在真实浏览器里跑的冒烟测试（可选，需要一次性安装 Chromium）：

```bash
corepack pnpm browser:install && corepack pnpm test:lab:browser
```

它会自己起服务、遍历全部演示与视图标签、拖动时间轴、检查三种检查状态的渲染、
验证成对参数无法被拖成非法组合，并检查导出的 SVG / JSON 内容。
也可以在页面控制台里直接调用 `runSmoke()`。

测试分四类：

- **契约**：轨迹格式良好，事件时间单调，**每条消息恰好以一次送达或丢弃收尾**
  （运行结束时仍在途中的消息会以 `simulation_end` 记为丢弃），
  声明的视图与轨迹实际输出的视图一致，每项检查只报三种状态之一。
- **正向**：正确配置在多个预先声明的种子下保持全部不变式。
- **反向**：故意设错的配置**必须**给出反例。一个永远不会失败的演示，
  什么也证明不了——所以 `ack=local`、`retry=new_id`、`commit_rule=naive_majority`
  都被要求产生对应的违反。
- **讲稿**：本文件里出现的每个具体数字都有对应断言，改了实现而忘了改讲稿会让测试失败。

### 检查结果有三种状态

| 状态 | 含义 | 界面 |
|---|---|---|
| 通过 pass | 这次运行里该性质成立 | 绿色 |
| 违反 fail | 找到了反例，可一键跳到那一刻 | 红色 |
| **未检查 inconclusive** | 检查器因为规模上限放弃了，什么也没证明 | 灰色虚线框 |

线性一致检查是穷举搜索，单键历史超过 14 个操作时会进入第三种状态。
**未检查不是通过**：它在 `summary.inconclusive` 里单独列出，不计入违反，
界面也不会给它绿色。把 `jepsen-loop` 的操作数调到 20 就能看到这个状态。

## 与课件的关系

lab 复用课件里出现过的模块，学生在动画里看到的就是幻灯片上的那段代码：

- `examples/raft_rules.py` — 投票的日志新旧比较、当前任期提交条件
- `examples/sharding.py` — 稳定散列与倾斜工作负载。测试里有一条子进程用例：
  换 `PYTHONHASHSEED` 重跑，分片映射必须完全一致。
- `examples/lamport_clock.py` — `four-clocks` 里的 Lamport 规则就是这个类
- `examples/history_checker.py` — 线性一致检查。lab 的检查器额外处理 unknown 结果，
  测试里有一条一致性用例：在“全部操作都已返回”的历史上，两者判定必须完全一致。

lab 是独立包：不改动 `slides/`，也不参与 `pnpm build` 与 `pnpm check`。

## 边界

- **不是生产实现**。教学版 Raft 简化了持久化细节，不实现成员变更；
  快照与日志压缩是简化实现（见 `snapshot-catchup`），不含增量快照与分块传输。
- **不是性能基准**。所有时间都是逻辑 tick，不可与真实系统比较。
- **多数派按配置成员总数计算**，即 `n // 2 + 1`。崩溃或不可达的节点仍然属于配置，
  只是不能贡献选票或确认；因此故障过多时系统失去可用性，**而不会自动缩小多数派**。
  如果多数派随存活节点缩小，两个互不相交的“多数派”就可能同时成立，安全性随之崩塌。
  代码里始终使用固定的成员数：`majority(len(self.cluster.node_ids))`。
- **线性一致检查是穷举搜索**，单键操作数超过 14 时不做检查，界面会明说“这不是通过，是未检查”。
- **AP 与 2PC 都是教学模型**：AP 只做日志尽力传播，不含冲突合并；
  2PC 的参与者是单事务锁、无死锁检测，重点在 prepared 义务与决议持久化。
- **均衡阈值是声明出来的**（最热分片 ≤ 平均值的 2.5 倍），不是客观标准；报告里要写出阈值。
- **ARIES 是两页四键的物理 undo 模型**：重点在两条落盘先后规则与三个阶段，
  不涉及页面结构、逻辑 undo 与细粒度锁。
- **`four-clocks` 是固定事件脚本**：正因为因果关系完全已知，才能拿它检查时钟的判断。
- **查询代价模型是教学化的**：固定行宽、线性带宽与 CPU，用于比较策略之间的量级，不是性能基准。
  但 Join **真的会执行**，所以“少返回行”是真实的结果差异，不是模拟出来的告警。
- **`architecture-lenses` 是路径模型**：只比较协调与等待发生在路径的哪一段，
  不代表任何产品的实测行为。相关官方文档见仓库根目录的 `sources.md`。
- **`jepsen-loop` 的搜索规模是课堂规模**：默认 12 个种子、每轮 9 个操作，
  线性一致检查器是穷举搜索。找不到反例只说明这些调度里没找到。
